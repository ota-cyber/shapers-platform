# Infrastructure

One page: services, how they connect, environment variables, and how to deploy from zero.

## Services

| Service | What it does | Plan |
|---|---|---|
| **Supabase** | Postgres (all data, rules and analytics as SQL), Auth (sign-in), one Edge Function (`sync-calendar`) | Free |
| **Google Calendar** | Source of all meetings. Read only, through the public Calendar API with an API key | Free |
| **Vercel** | Hosts the Next.js web app (`src/`) | Free |
| **Slack** | Finished tasks are shared in the team channel (Incoming Webhook, posted by the database) | Free |

```
Browser ──supabase-js (anon key + user session)──► Supabase API ──► Postgres (RLS on every table)
                                                       │
Admin "Sync calendar" ──► Edge Function sync-calendar ─┴─► Google Calendar API (read only)
```

Nothing writes to Google Calendar. Finished tasks are posted to Slack by the database (`task_done_to_slack`).

## Repository layout

| Path | Contents |
|---|---|
| `supabase/migrations/` | Schema, business rules (RPCs, triggers), views for dashboards, row-level security |
| `supabase/seed.sql` | Sandbox data: 20 members, 55 meetings, attendance, 6 weeks of hours, demo projects and tasks. Generated by `scripts/build_seed.py` |
| `supabase/functions/sync-calendar/` | Google Calendar → `meetings` |
| `scripts/create-demo-users.mjs` | One sign-in per sandbox member with the demo password |
| `scripts/smoke-test.mjs` | End-to-end check over the API (52 checks) |
| `sandbox/` | The organisers' sandbox files (made-up data) |
| `types/database.ts` | Generated TypeScript types |

## Environment variables

| Name | Where | Value |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | frontend (Vercel) | Project URL (Supabase → Project Settings → API) |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | frontend (Vercel) | Public anon key (same page) |
| `NEXT_PUBLIC_DEMO_PASSWORD` | frontend (Vercel), optional | Demo password used by "View as" (default `shapers-demo`) |
| `SUPABASE_URL`, `SUPABASE_ANON_KEY` | scripts | Same values as above, for the scripts |
| `SUPABASE_SERVICE_ROLE_KEY` | scripts only, never the frontend | Service role key (same page) |
| `DEMO_PASSWORD` | scripts | Password given to every sandbox sign-in (at least 6 characters; same value as `NEXT_PUBLIC_DEMO_PASSWORD`) |
| `GOOGLE_CALENDAR_ID` | Edge Function secret | Calendar ID of the imported sandbox calendar |
| `GOOGLE_API_KEY` | Edge Function secret | Google Cloud API key with the Calendar API enabled |
| `NEXT_PUBLIC_VAPID_PUBLIC_KEY` | frontend (Vercel) | Web Push public key; see [NOTIFICATIONS.md](NOTIFICATIONS.md) |
| `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` | Edge Function secrets | Web Push signing for `send-notifications` |

Without `NEXT_PUBLIC_SUPABASE_URL` the web app runs on built-in demo data in the browser.

## Deploy from zero

Needs: Node 18+, the [Supabase CLI](https://supabase.com/docs/guides/cli), a Supabase account, a Google account.

1. **Calendar.** Import `sandbox/meetings.ics` into a new Google Calendar ("Sandbox"), make it public
   (Settings → the calendar → Access permissions → Make available to public), copy its Calendar ID.
   In Google Cloud, enable the Google Calendar API and create an API key.
2. **Supabase project.** Create a project at supabase.com. Then, in this repo:
   ```sh
   supabase login
   supabase link --project-ref <project-ref>
   supabase db push --include-seed        # schema, rules, views, security + sandbox data
   supabase functions deploy sync-calendar
   supabase secrets set GOOGLE_CALENDAR_ID=<id> GOOGLE_API_KEY=<key>
   ```
3. **Sign-ins for the sandbox members.**
   ```sh
   SUPABASE_URL=... SUPABASE_SERVICE_ROLE_KEY=... DEMO_PASSWORD=... node scripts/create-demo-users.mjs
   ```
4. **Check it.** `SUPABASE_URL=... SUPABASE_ANON_KEY=... SUPABASE_SERVICE_ROLE_KEY=... DEMO_PASSWORD=... node scripts/smoke-test.mjs`
   (writes test data; run it on a fresh project or skip it).
5. **Frontend.** Import the repository into Vercel (framework: Next.js, defaults are fine) and set
   `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` and `NEXT_PUBLIC_DEMO_PASSWORD`. Deploy.
6. **Google sign-in.** In Google Cloud → APIs & Services → Credentials, create an **OAuth client ID** (Web application)
   with the authorised redirect URI `https://<project-ref>.supabase.co/auth/v1/callback` (OAuth consent screen: External,
   scopes email and profile only, published). In Supabase → Authentication → Sign In / Providers → Google, paste the
   client ID and secret. In Supabase → Authentication → URL Configuration, set the Site URL to the Vercel URL and add it
   to the redirect URLs. A Google account signs in as the member with the same email; an admin adds new people in
   Team → Quick add. The demo people sign in with the demo password from the sign-in screen.

## Slack

Create a Slack app with an **Incoming Webhook** for the team channel, then store its URL in the database
(Supabase → SQL editor; it lives in the `private` schema, which the API never serves):

```sql
insert into private.settings values ('slack_webhook_url', 'https://hooks.slack.com/services/…')
on conflict (key) do update set value = excluded.value;
```

## Changing things later

- New migrations: `supabase db push` (without `--include-seed`, so live data stays).
- Tier rules (hours, rule texts, notice hours), onboarding and setup steps and thresholds (`app_settings`) are rows in the
  database; edit them in the Supabase table editor and the app shows the change on the next load.
- New people: anyone can sign in with Google; they appear in Team → Approvals and become GO! members when approved.
- Testing onboarding again: sign in as a GO! test member → You → Settings → **Restart my onboarding** (RPC
  `restart_onboarding`; admins can't be restarted).

## Local development

```sh
supabase start                      # Docker; prints local URL and keys
supabase db reset                   # migrations + seed
node scripts/create-demo-users.mjs  # with the local URL/keys from `supabase status -o env`
```
